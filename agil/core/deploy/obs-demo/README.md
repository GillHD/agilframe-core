# Эфир из OBS в «Паприке»

MediaMTX принимает эфир из OBS. При создании ведущий выбирает RTMPS → HLS для обычного эфира или WHIP → WHEP для минимальной задержки. Сервер выдаёт отдельный ключ публикации, ссылку для зрителей и токен завершения. У каждого эфира свой набор. Ключ подходит для переподключения OBS в пределах того же эфира. Ссылка для зрителей даёт доступ каждому, кому её передали. Сервис хранит состояния в памяти, завершает эфир при удалении или истечении срока. Перезапуск закрывает предыдущие эфиры. Значения по умолчанию дают 30 минут и до трёх эфиров одновременно на экземпляр.

## Развёртывание

1. Скопируйте `.env.example` в `.env`. Укажите канонический HTTPS-адрес embedded call, origin «Паприки» и адрес RTMPS, заканчивающийся на `/obs`. Сгенерируйте два независимых случайных ключа, например двумя вызовами `openssl rand -hex 32`. Код организатора передайте уполномоченным ведущим.
2. Подготовьте сертификат публичного центра для хоста RTMPS в `AGIL_OBS_CERT_DIR`. Контейнер ожидает `fullchain.pem` и `privkey.pem`. Обновление сертификата включите в штатную процедуру обновления. [Требования OBS к TLS](https://mediamtx.org/docs/publish/obs-studio#encryption-rtmps).
3. Запустите `docker compose up -d` из этой директории. Во внешнем прокси embedded call направьте только `/obs-demo/*` в брокер с сохранением полного URI. Для прокси на хосте адрес брокера `127.0.0.1:18898`. Для прокси в Docker соедините его с сетью брокера и используйте `broker:8898`. Откройте TCP 1936 для RTMPS и UDP 8189 для WebRTC. `AGIL_OBS_ICE_HOST` должен разрешаться в адрес, достижимый для клиента. Для сетей, где прямое ICE-соединение недоступно, настройте TURN и проверьте соединение из такой сети. Управляющий API MediaMTX, внутренний callback и HLS-порт MediaMTX используют приватную сеть. [Сеть WebRTC](https://mediamtx.org/docs/features/webrtc-specific-features).
4. В «Паприке» откройте «Трансляции и записи» → «Эфир из OBS Studio», введите код и выберите режим. В OBS откройте «Настройки» → «Трансляция». Для HLS выберите «Пользовательский», скопируйте сервер и ключ. Используйте H.264 и AAC, интервал ключевых кадров 2 секунды. Для WebRTC выберите WHIP и вставьте адрес сервера и токен Bearer. Используйте H.264 и Opus. [OBS и MediaMTX](https://mediamtx.org/docs/publish/obs-studio).
5. Откройте ссылку зрителя в другой вкладке. После начала потока в плеере появится видео. Нажмите «Завершить эфир» на странице организатора и дождитесь завершения у зрителя.

## Локальная проверка

Укажите название эфира и включите показ в списке, чтобы зрители могли найти его без приглашения. Этот режим также включает чат. Организатор может модерировать сообщения и авторов. Для непубличного эфира зрители используют выданную ссылку. Плеер загружает до 80 сообщений на страницу. История хранится в SQLite, а для записанного эфира доступна до истечения срока повтора.

Повтор включается отдельным переключателем для HLS. MediaMTX пишет медиа в том `recordings`, брокер сохраняет метаданные в томе `broker-state`. После закрытия по прежней ссылке открываются записанные части. Хранилище рассчитано на 24 часа, локальный API воспроизведения MediaMTX доступен только брокеру. После рестарта брокера активный эфир закрывается, готовые части остаются доступными. Эфир по WebRTC можно смотреть вживую. Повтор в этом режиме пока не предлагается.

Для проверки чата и повтора добавьте `--public-replay` к `workshop-obs-e2e.mjs`. В локальной конфигурации подключите порт воспроизведения MediaMTX и отдельный каталог метаданных через `AGIL_OBS_MTX_PLAYBACK_URL` и `AGIL_OBS_REPLAY_DIR`. Проверьте рекламируемую ссылку в новом профиле браузера, отправку сообщения, права модератора и воспроизведение после остановки. [Запись MediaMTX](https://mediamtx.org/docs/features/record) · [Воспроизведение MediaMTX](https://mediamtx.org/docs/features/playback)

Используйте MediaMTX 1.21.4 и Node.js. Для локальной лаборатории включите обычный RTMP в конфигурации MediaMTX и привяжите RTMP, управляющий API и HLS к `127.0.0.1`. Включите `authMethod: http` и задайте `authHTTPAddress` в формате `http://127.0.0.1:18898/internal/media-auth/<callback-key>`. Остальные параметры возьмите из `mediamtx.yml`, пропустив поля TLS. Брокеру передайте соответствующие адреса и два ключа через окружение. Для браузерного сценария используйте `http://127.0.0.1:18765` для статического сайта и `http://127.0.0.1:18898` для брокера. `AGIL_OBS_PORT=18898` задаёт порт брокера.

`node agil/core/qa/workshop-obs-e2e.mjs` проверяет выдачу ключей и живую передачу заранее закодированного H.264/AAC через FFmpeg. С `--realtime` передача идёт через WHIP и Chromium принимает WHEP. Укажите `AGIL_OBS_MTX_WEBRTC_URL` и настройте локальный ICE в MediaMTX. Организатор завершает эфир, а новый эфир получает отдельные ключ и ссылку. Для сквозной проверки OBS вручную повторите шаги 4–5 с OBS Studio.

## Чат эфира

Брокер по умолчанию сохраняет последние 100 000 комментариев каждого эфира в локальный файл SQLite на томе. Отдельный сервер БД не нужен. Для запуска без тома задайте `AGIL_OBS_CHAT_FILE=:memory:`. При ручном запуске используйте современный Node.js с `node:sqlite`, в Compose используется Node.js 24. Для файлового режима используйте один брокер на том и включите файл в политику резервных копий. Несколько экземпляров потребуют общего хранилища комментариев и общих счётчиков антиспама.

Плеер получает до 80 комментариев за запрос. Кнопка «Ранние сообщения» использует курсор `before` из `GET /obs-demo/sessions/{id}/chat`. Запросы последних сообщений поддерживают `ETag`. Для записанного эфира `?archive=1` открывает архив для чтения до срока повтора. Комментарии эфира без повтора становятся недоступны при его завершении. Фоновая очистка удаляет просроченные данные из SQLite. Срок хранения резервных копий задаётся отдельно.

| Переменная | Значение по умолчанию |
| --- | --- |
| `AGIL_OBS_CHAT_FILE` | `/state/chat/comments.sqlite` в Compose. |
| `AGIL_OBS_CHAT_LIMIT` | `100000` записей по последним ID. Допустимо до `1000000`. |
| `AGIL_OBS_CHAT_SOURCE_PER_MINUTE` | `12` попыток в минуту на пропуск зрителя, начальный всплеск до трёх попыток. |
| `AGIL_OBS_CHAT_STREAM_PER_SECOND` | `100` принятых комментариев в секунду на эфир с запасом на короткий всплеск. |
| `AGIL_OBS_CHAT_TRUSTED_PROXIES` | По умолчанию пусто. Через прокси перечислите точные IP его TCP-подключений к брокеру. |

Ограничения действуют на POST и возвращают `429` с `Retry-After`. Текст повторной отправки нормализуется. Повтор с одного источника ограничивается 30 секундами, а одинаковый длинный текст с разных источников ограничивается шестью отправками за 15 секунд. Удалить комментарий во время эфира можно с ключом управления этого эфира.

За прокси настройте перезапись заголовка `X-Agil-Client-IP` адресом клиента, который установил сам доверенный прокси. Например, для Nginx с корректно настроенным адресом клиента задайте `proxy_set_header X-Agil-Client-IP $remote_addr;`. Закройте прямой доступ к порту брокера. По сети действует только краткий общий лимит запросов. Блокировки отправки привязаны к пропуску зрителя.

### CAPTCHA и блокировки

Пропуск зрителя выдаёт `POST /obs-demo/sessions/{id}/chat/identity`. Клиент передаёт `credential` при отправке комментария. Паприка сохраняет пропуск в хранилище браузера на время эфира и повторно использует его после перезагрузки. Он случайный, подписан брокером и ограничен одним эфиром. Имя и IP не используются для подтверждения личности. Видеоплеер и чтение чата доступны без пропуска. Удаление данных сайта сбрасывает локальную анонимную сессию. Для устойчивых банов между браузерами и устройствами потребуется вход с проверенным идентификатором аккаунта. [Рекомендации W3C по отпечаткам браузера](https://www.w3.org/TR/fingerprinting-guidance/)

В окне «Модерация эфира» откройте «Фильтр сообщений». Можно ограничить распространённые ссылки и задать до 50 буквальных фраз длиной от 3 до 100 символов. Брокер проверяет имя и текст, останавливает совпадения до публикации и возвращает зрителю причину. Базовый фильтр блокирует небезопасные схемы и активную разметку. Текст комментариев отображается как текст. Настройки действуют до завершения эфира. Содержимое сайтов по URL не анализируется. [Проверка свободного ввода OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)

Чтобы запретить зрителю писать до конца эфира, нажмите «Заблокировать» рядом с его сообщением. Другие браузеры с собственным пропуском, в том числе на том же IP, сохраняют доступ. «Снять бан» доступно в списке блокировок. Старые сообщения удаляются отдельной кнопкой. Пропуск и идентификатор зрителя не выдаются в публичной истории. После завершения записи идентификаторы очищаются из архивных строк.

1. В Cloudflare Turnstile создайте виджет для hostname из `AGIL_OBS_SITE_ORIGIN`. Передайте брокеру публичный `AGIL_OBS_TURNSTILE_SITE_KEY` и секретный `AGIL_OBS_TURNSTILE_SECRET_KEY`. Брокеру нужен HTTPS-доступ к `challenges.cloudflare.com`. Если используется CSP, разрешите этот origin в `script-src` и `frame-src` страницы просмотра. [Настройка Turnstile](https://developers.cloudflare.com/turnstile/get-started/)
2. В эфире напишите комментарий и нажмите «Отправить». После проверки браузер сохранит подтверждение CAPTCHA в памяти вкладки на 10 минут. Оно привязано к этому эфиру и пропуску зрителя. История и видео доступны до прохождения проверки. При недоступности Siteverify новые проверки приостанавливаются, действующие подтверждения сохраняют силу до истечения. Если обе переменные пусты, работает встроенный антиспам без CAPTCHA. Если задан только один ключ, брокер сообщит об ошибке конфигурации при старте. [Проверка Siteverify](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)
3. В панели управления текущим эфиром откройте «Модерация эфира». Карточка показывает последнее известное имя с пометкой «Имя указано зрителем», причину, время начала и окончания блокировки. Кнопка `i` раскрывает IPv4 или сеть IPv6 `/64`. Чтобы видеть список во время чтения чата, включите «Показывать в чате». Этот переключатель действует только в окне организатора и сбрасывается при смене эфира.
4. Приложение организатора читает список через `GET /obs-demo/sessions/{id}/chat/blocked` с `Authorization: Bearer <manageToken>` текущего эфира. В ответе `blocks` содержит `name` или `null`, `address`, `reason`, `blockedAt` и `blockedUntil` в миллисекундах Unix. После восьми нарушений за минуту брокер блокирует отправку с источника на пять минут. Сведения о блокировке и последнее известное имя источника хранятся в памяти до завершения эфира или перезапуска. Архив содержит опубликованные комментарии без IP-адресов и пропусков.

## Узлы просмотра

Брокер выдаёт браузеру до трёх адресов для выбранного протокола. Браузер параллельно проверяет их из сети зрителя с тайм-аутом 800 мс. Каждый узел по запросу подтягивает один поток с узла приёма и раздаёт его своим зрителям. Во время нормального воспроизведения повторных проверок нет. [Работа MediaMTX с источниками по запросу](https://mediamtx.org/docs/references/configuration-file).

- `AGIL_OBS_EDGE_ROUTING=latency` выбирает узлы в пределах 15 мс от самого быстрого.
- `AGIL_OBS_EDGE_ROUTING=load` сравнивает загрузку всех ответивших узлов.
- `AGIL_OBS_EDGE_ROUTING=balanced` по умолчанию сравнивает загрузку среди узлов в пределах 60 мс от самого быстрого.

При близких результатах сохраняется порядок брокера, который распределяет вкладки по узлам. Разница до 5 процентных пунктов загрузки считается близкой. При отсутствии метрик хотя бы у одного сравниваемого узла используется время ответа. Если проверка недоступна на всех адресах, плеер пробует первый адрес.

1. На узле приёма задайте `AGIL_OBS_RELAY_ENABLED=true`, приватный `AGIL_OBS_RELAY_BIND` и отдельный `AGIL_OBS_RELAY_KEY`. Ограничьте доступ к TCP 8554 сетью узлов просмотра. На каждом узле просмотра запустите свой MediaMTX с `mediamtx-edge.example.yml`. Укажите приватный адрес узла приёма и ключ ретрансляции. Если узлы находятся на разных машинах, укажите приватный `AGIL_OBS_BROKER_BIND` и направьте прокси embedded call на этот адрес. Узлы вызывают внутренний callback только по приватной сети. Он проверяет, действует ли эфир. Публичный доступ к плеерам обеспечьте через HTTPS.
2. Для каждого узла укажите пару HTTPS-origin в `AGIL_OBS_EDGES`, например `[{"hls":"https://hls1.example.com","realtime":"https://rtc1.example.com"},{"hls":"https://hls2.example.com","realtime":"https://rtc2.example.com"}]`. Проксируйте origin HLS на порт 8888 и origin WebRTC на 8889. Сохраняйте пути `/obs/...` и заголовки сессии WHEP. Для WebRTC укажите публичный ICE hostname узла и откройте его UDP-порт 8189.
3. Прогоните сценарий с `--edges` и с `--edges --realtime`. Два профиля браузера получают разные адреса просмотра. Брокер выдаёт адрес и статус, медиатрафик идёт напрямую с узлов просмотра.

Для режимов `load` и `balanced` добавьте к каждой записи `AGIL_OBS_EDGES` поля `"control":"http://edge1.private:9997","hlsCapacity":500,"realtimeCapacity":100`. Значения ёмкости здесь приведены для примера. Подберите их под своё железо и профили видео. Брокер раз в три секунды при запросах на назначение суммирует доли активных HLS- и WebRTC-сессий от соответствующих лимитов. Это оценка нагрузки по соединениям. Ограничьте доступ к Control API приватной сетью и разрешите его только брокеру. При совместном запуске оставьте адрес API на loopback, как в примере MediaMTX. Никогда не маршрутизируйте Control API через публичный прокси. [Control API MediaMTX](https://mediamtx.org/docs/references/control-api).

Для выбора по доступности откройте `GET /obs-demo/ready` на каждом HTTPS-origin просмотра. Эндпоинт должен возвращать HTTP 204 только при работоспособном HTTP-сервисе MediaMTX за прокси. Ответу нужны `Cache-Control: no-store` и CORS для origin «Паприки». Он проверяет доступность HLS или сигналинга WHEP из браузера. Проходимость ICE и скорость передачи медиа подтверждаются при воспроизведении.

Пример для Nginx на HLS-узле. У MediaMTX 1.21.4 корневой путь возвращает 404 даже без активных эфиров. Для адреса WHEP замените порт 8888 на 8889. Подставьте свой origin «Паприки».

```nginx
location = /obs-demo/ready {
    proxy_pass http://127.0.0.1:8888/;
    proxy_cache off;
    proxy_connect_timeout 500ms;
    proxy_read_timeout 500ms;
    proxy_intercept_errors on;
    error_page 404 = @obs_ready;
}

location @obs_ready {
    add_header Access-Control-Allow-Origin "https://workshop.example.com" always;
    add_header Cache-Control "no-store" always;
    return 204;
}
```

Флаг `--probe-routing` подставляет задержку и HTTP 503 только для проверочных запросов в двух браузерах. Плейлист HLS, WHEP и медиаданные идут через реальные экземпляры MediaMTX. Флаг `--load-routing` проверяет выбор третьего зрителя по фактическим сессиям MediaMTX. Для этого задайте ёмкость первого узла 1 и второго 500 для обоих протоколов и включите `balanced` или `load`. Добавьте `--realtime` для прогона WebRTC.

При ошибке соединения или остановке кадров плеер запрашивает следующий узел. Вкладка пропускает уже недоступные ей узлы. Если узлы закончились, кнопка «Повторить» сбрасывает этот список. Исходная передача продолжается на том же узле приёма.

Для проверки отказа добавьте `--failover` к сценарию. Укажите пути к MediaMTX и конфигурации первого узла через `AGIL_QA_OBS_MEDIA_BIN` и `AGIL_QA_OBS_FIRST_EDGE_CONFIG`. Настройте первый HLS-адрес на `http://127.0.0.1:38888` и оставьте его выключенным перед запуском. Тест сам запускает этот экземпляр, дожидается видео в двух профилях, останавливает экземпляр и подтверждает декодирование через другой адрес при работающем источнике. Для WebRTC добавьте `--realtime`.

Приём OBS пока ведёт один экземпляр. Для назначения разных узлов приёма требуется общий реестр эфиров с выбранным origin, проверка здоровья и ёмкости узлов, выдача прямого ingest-адреса и стратегия переподключения OBS.

Общий API назначает узел до начала передачи и возвращает его адрес в ответе. Для зрителя можно оставить короткую ссылку на страницу «Паприки», где клиент разрешает адрес через API. HLS оставляет выбранный узел на время просмотра, а WHEP привязывает адрес сигналинга к конкретному ICE-соединению. При смене узла плеер открывает новую сессию. DevOps-балансировщик распределяет запросы общего API и трафик CDN, а приложение управляет размещением эфиров и назначением узлов.

| 1 | Статус входящего сигнала и диагностика | Брокер показывает ведущему кодеки, разрешение и входящий битрейт. Следующий шаг — причины обрыва и журнал изменений состояния. [Метрики Flashphoner](https://docs.flashphoner.com/pages/viewpage.action?pageId=14254144) |

| 3 | Адаптивные профили HLS и CDN | Нужно для массовой аудитории и слабых сетей после замера нагрузки. Локальный брокер выдаёт входной профиль. Многопрофильное кодирование потребует отдельной мощности. [CDN и транскодирование Flashphoner](https://docs.flashphoner.com/static/WCS53/) |
| 4 | WHIP и просмотр WebRTC | Добавлен отдельный режим эфира. Следующий шаг — замер сквозной задержки, подключений через TURN и числа зрителей на узел. [Входы и выходы Flashphoner](https://docs.flashphoner.com/static/WCS53/) |

Flashphoner описывает серверное подтверждение публикации и отдельное правило просмотра через [REST Hooks](https://docs.flashphoner.com/static/WCS53/REST_Hooks/A_kinds_of_REST_hooks/Type_2_-_the_direct_invoke/) и [HLS](https://docs.flashphoner.com/pages/viewpage.action?pageId=90866043).
