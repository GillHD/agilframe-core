# SFU multi-node (LiveKit + Redis + Caddy)

Дата: 15.11.2026. Цель — убрать single-point и проверить маршрутизацию
нескольких LiveKit-узлов через общий Redis.

## Схема

```
browser ──wss──► Caddy :9443 (round_robin)
                    ├─► livekit-1 127.0.0.1:7880  RTC 50000–50100 / 7881
                    └─► livekit-2 127.0.0.1:7890  RTC 50200–50300 / 7891
                                   │
                                   └─ Redis 6379 (shared room directory + bus)
```

- `livekit-1`: node ID `ND_qfScbnX6uoMx` (порт 7880).
- `livekit-2`: node ID `ND_nCsZ6qCA99os` (порт 7890, RTC 50200–50300).
- Caddy распределяет соединения `sfu.example.com` между двумя LiveKit по `round_robin`. Пример конфигурации проверяет `GET /` каждые три секунды. При ошибке подключения он временно исключает неответивший upstream и ищет доступный до пяти секунд.
- HAProxy по SNI направляет `sfu.example.com` в Caddy.

## Проверка

- Оба узла стартуют, видят Redis, отдают `GET /` → 200.
- Два реальных браузера (Chrome, fake media) подключаются к `wss://sfu.example.com` через Caddy:
  - в логах `roomallocator` выбран узел **`ND_nCsZ6qCA99os`** (livekit-2);
  - оба участника активны, публикуют audio/video, у обоих 2 плитки и remote-видео **320×180** (`readyState=4`), 0 ошибок консоли;
  - signalling-соединения приходят через Caddy на разные узлы и бриджатся к узлу комнаты (LiveKit Redis message bus).
- Room media идёт через RTC-порт **50238/50291** (node2, UDP), т.е. второй узел реально обслуживает комнату.

### Локальное восстановление после потери узла

Повторяемый сценарий запускает два LiveKit с общим Redis и временный Core.
Первый браузер входит через A. Второй входит через B и получает медиа комнаты
с A. Список участников из B совпадает с идентификаторами обеих плиток.

```powershell
$env:AGIL_QA_REDIS_BIN = 'C:/path/to/redis-server.exe'
node --import tsx agil/core/qa/widget/sfu-multinode-e2e.mjs
```

Для Redis в `PATH` переменная не требуется. Путь к LiveKit можно задать через
`AGIL_QA_LIVEKIT_BIN`, начальный порт через `AGIL_QA_SFU_CLUSTER_PORT`.
Сценарий создаёт свои процессы на loopback и завершает их после проверки.

Режим `--direct-nodes --toggle-sfu` проверяет изменение возможностей ноды при
действующем звонке. Core исключает ноду из новых назначений после отключения
SFU, сохраняет уже назначенную комнату и возвращает ноду в пул после включения
функции и нового отчёта готовности. Сценарий проверяет обе правки в аудите.

Для проверки предпочтительной ноды запустите сценарий с
`--direct-nodes --drain --pin-primary`. В этом режиме `AGIL_SFU_NODE_ID`
указывает на первую ноду в карте прямых адресов. Локальный прогон подтвердил,
что достигшая лимита или выведенная в обслуживание нода уступает место второй.
Действующая комната сохранила AV1 на прежних соединениях и смогла принять ещё
одного участника. После её завершения первая нода штатно остановилась.

На LiveKit 1.13.11 с локальным Redis для Windows 5.0.14.1 оба Chromium
декодировали AV1 640×360 через UDP на A. После аварийной остановки A оба
браузера снова декодировали кадры на B через **14,8 с**. Идентификаторы
участников в плитках и реестре LiveKit сохранились. Новая комната также
запустилась на B с двусторонним видео. Маршрутизацию сигналинга задавал
тестовый прокси. В повторе на локальном хосте видео вернулось за 14,3 с.
TURN между разными сетями требует отдельного прогона.
Сценарий · [Документация LiveKit](https://docs.livekit.io/transport/self-hosting/distributed/) · [Сборка Redis для Windows](https://github.com/tporadowski/redis/releases/tag/v5.0.14.1).

### Плановый вывод SFU из работы

```powershell
node --import tsx agil/core/qa/widget/sfu-multinode-e2e.mjs --drain
```

На Windows нужен Python 3.8+ в `PATH`. Тестовый помощник посылает
`Ctrl+Break` только процессу LiveKit A в отдельной консольной группе.
На Linux сценарий посылает A `SIGTERM`. Начало drain подтверждает журнал
LiveKit: узел ждёт выхода участников.

Локальный прогон на Windows с LiveKit 1.13.11 и прямым UDP подтвердил:

1. Оба участника продолжили декодировать AV1 на A. Счётчики выросли на тех
   же входящих дорожках и WebRTC-соединениях, идентификаторы участников сохранились.
2. Новая комната получила двустороннее видео на B, пока A продолжал
   обслуживать первую комнату.
3. Третий участник вошёл в первую комнату через сигналинг A и получил видео
   с A. Запрос реестра через B увидел всех троих.
4. После выхода троих через кнопку звонка A завершился с кодом 0.
   От первого нажатия до завершения прошло 5,1 с. Оба клиента второй
   комнаты продолжили декодировать видео на B.

Маршрутизацию сигналинга в этом прогоне задавал тестовый прокси.
Сценарий · [Режим drain LiveKit](https://docs.livekit.io/transport/self-hosting/distributed/#downscaling-and-draining).

### Проверка с принудительным TURN/UDP

```powershell
$env:AGIL_QA_TURN_IP = '<IPv4 тестового хоста>'
$env:AGIL_QA_SFU_LOG_DIR = '.tmp/sfu-turn'
node --import tsx agil/core/qa/widget/sfu-multinode-e2e.mjs --relay
```

Сценарий поднимает встроенный TURN на каждом тестовом узле. Chromium
использует `iceTransportPolicy: relay`. Для успешного шага требуется выбранная
ICE-пара с локальным кандидатом `relay` и декодированные кадры от нужного
узла. Вывод при отказе содержит состояния ICE, пары кандидатов и счётчики
ответов. [Конфигурация TURN LiveKit 1.13.11](https://github.com/livekit/livekit/blob/v1.13.11/config-sample.yaml).

На одном Windows-хосте два Chromium декодировали AV1 640×360 через TURN/UDP
узла A. После его остановки браузеры получили адрес TURN на B и выделили
relay-кандидаты. Установить ICE-пару и восстановить видео за 45 секунд не
удалось. В контрольной попытке новый звонок на B также завершился ожиданием
подключения. В серверном журнале пара B отправила восемь ICE-запросов без
ответа. Прогон через прямой UDP служит отдельной проверкой размещения и
восстановления; внешние сети и TURN/TLS ещё предстоит проверить.

Для сравнения с отдельным TURN на том же тестовом хосте задайте
`AGIL_QA_TURN_EXTERNAL_PORT`, `AGIL_QA_TURN_USER` и `AGIL_QA_TURN_PASSWORD`
с временными учётными данными. Оба LiveKit передадут Chromium один адрес TURN.
Запуск без `--relay` с `AGIL_QA_SFU_MEDIA_IP`, равным `AGIL_QA_TURN_IP`, проверяет
прямой UDP на том же интерфейсе.

Повтор с отдельным Pion TURN 4.0.0 подтвердил двустороннее видео на первом
узле. При переходе на второй Chromium выделил relay-кандидат на том же TURN,
отправил 56 ICE-запросов и не получил ответов. Когда прежний второй узел
запустили первым на том же медиапорте, отказ возник уже при первом входе:
TURN зарегистрировал исходящий STUN Binding Request к SFU, ответ не пришёл.
Диагностика указывает на участок между relay и медиатранспортом SFU.
В прямом UDP на том же IPv4 активный звонок восстановился через 14,5 с,
новый звонок также получил двустороннее видео. [Pion TURN](https://github.com/pion/turn/tree/v4.0.0).

#### Внешний TURN в отдельной виртуальной сети

Два Chromium и два LiveKit работали на Windows, а Pion TURN 4.0.0 —
в сети WSL 2. Адрес relay из выбранной ICE-пары принадлежал WSL, адрес
медиакандидата SFU — виртуальному интерфейсу Windows. Со встроенным и с
отдельным TURN переход на диапазоны UDP-портов позволил восстановить
действующий звонок. Новый звонок всё ещё срывался при входе участника.

В повторе ограничили сбор ICE-кандидатов адресом интерфейса Windows,
доступным из WSL (`rtc.ips.includes`). Активный звонок восстановил
двустороннее видео AV1 на B за 14,5 с с раздельными UDP-портами
и за 14,3 с с UDP mux. В обоих прогонах новая комната на B тоже получила
двустороннее видео через тот же relay. Контрольный прогон с тем же фильтром,
UDP mux и встроенным TURN на интерфейсе Wi-Fi Windows также прошёл
восстановление за 14,5 с и вход в новую комнату. Выбор ICE-адресов при развёртывании
зависит от того, какие интерфейсы доступны клиентам и TURN.
[Параметры LiveKit](https://github.com/livekit/livekit/blob/v1.13.11/config-sample.yaml) · [Порты LiveKit](https://docs.livekit.io/transport/self-hosting/ports-firewall/).

Для повтора с отдельным тестовым TURN задайте в `AGIL_QA_TURN_IP` адрес
медиаинтерфейса хоста SFU, а в `AGIL_QA_TURN_EXTERNAL_HOST` и
`AGIL_QA_TURN_EXTERNAL_PORT` адрес и порт TURN. Используйте временные
`AGIL_QA_TURN_USER` и `AGIL_QA_TURN_PASSWORD` или `AGIL_QA_TURN_SECRET`
для REST-аутентификации. У TURN должен быть доступ
к RTC-портам обоих SFU. Запустите сценарий с UDP mux, затем повторите
с `--udp-range` для отдельных портов на соединение.

```powershell
node --import tsx agil/core/qa/widget/sfu-multinode-e2e.mjs --relay --single-media-interface
```

Для TURN/TLS дополнительно задайте `AGIL_QA_TURN_EXTERNAL_PROTOCOL=tls`.
Если у тестового coturn собственный сертификат, передайте SHA-256 отпечаток
его SPKI в Base64 через `AGIL_QA_TURN_TLS_SPKI`. Сценарий проверяет
выбранную relay-пару и фактическое значение `relayProtocol` в Chromium.
Требуется свободный диапазон relay-портов для исходной комнаты,
переподключения и новой комнаты. Первый TLS-прогон с 15 портами восстановил
видео на B, а при создании ещё одной комнаты coturn ответил ICE-ошибкой 508.
После расширения стендового диапазона до 96 портов оба Chromium декодировали
AV1 1280×720 на A, сохранили идентификаторы при падении A и снова получили
двустороннее видео на B через 15,1 секунды. Новая комната на B также
передала видео в обе стороны. На каждом этапе выбранный ICE-кандидат был
типа `relay` с `relayProtocol=tls`. Coturn работал в WSL 2, LiveKit и
Chromium — на Windows.

Оба клиента этих прогонов находились на одном Windows-хосте. Стенд ниже
отдельно проверяет клиентов за двумя NAT.

### Переключение двух SFU с клиентами за двумя NAT

Два LiveKit 1.13.11 и общий Redis 7 работают в сегменте WSL 2 рядом с
отдельным coturn 4.6. Два Chromium работают в разных LAN и используют
независимые правила SNAT. Coturn видит адреса `198.18.90.2` и
`198.18.90.3` для клиентов с одинаковым LAN-адресом. Core работает на
Windows. Локальные прокси передают HTTP и WebSocket между Windows и
пространствами имён. RTP остаётся внутри тестовой сети.

При принудительном relay оба Chromium декодировали AV1 640×360 или 1280×720
и принимали Opus через медиапорт A 45682. После аварийной остановки A оба
восстановили звук и видео через порт B 45692 за 9,9 с с TURN/UDP и за
11,9 с с TURN/TLS. Отсчёт начинается перед командой остановки. Сохранились
идентификаторы участников и исходные WebSocket к Core. Новая комната на B
передала звук и видео в обе стороны. На всех этапах Chromium подтвердил
выбранную ICE-пару типа `relay` с протоколом текущего прогона.

Для воспроизведения нужны собранные серверные и веб-ресурсы репозитория,
WSL 2 с Docker, socat и Linux Chrome, а также локальные образы
`agil-node-all-in-one:qa-turn-tls`, `redis:7-alpine` и `coturn/coturn:4.6`.
Каждый запуск создаёт свою лабораторию и сохраняет журналы в `.tmp`.

```powershell
& agil/core/qa/widget/run-sfu-nat-e2e.ps1 -WslChromePath /path/to/chrome -Protocol udp
& agil/core/qa/widget/run-sfu-nat-e2e.ps1 -WslChromePath /path/to/chrome -Protocol tls
```

Стенд проверяет смену медиапорта, кодеки, выбранный relay, сохранение
соединения с Core и размещение новой комнаты. В роли общего входа работает
тестовый прокси, направляющий новые подключения к B. NAT независимы, оба SFU
работают в одной виртуальной машине WSL. Публичный DNS, сертификат оператора
и сети разных провайдеров требуют отдельной приёмки.

## Ограничения

- **Комната целиком живёт на одном узле** (так устроен LiveKit): multi-node
  масштабирует число комнат/тенантов и даёт HA, но не увеличивает лимит
  участников одной комнаты. Для одной комнаты 50+ нужен более мощный узел.
- Оба узла на одном 1 vCPU/2 GB — это проверка маршрутизации, не прирост
  ёмкости; для продакшена узлы должны быть на разных хостах/сетях.
- При падении узла открытые WebSocket-соединения обрываются. Проверка доступности Caddy действует на следующие подключения к сигналингу. Восстановление медиа активной комнаты зависит от повторного подключения LiveKit и требует отдельного браузерного теста с декодированием кадров. [Документация Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#active-health-checks)
- UDP-диапазоны узлов должны быть открыты на firewall (50200–50300 для node2).
