# Выбор хранилища Core и миграция данных

Ревью 27 ноября 2026. Core запускается без PostgreSQL. В первом этапе PostgreSQL обслуживает только явно включённую долговременную историю чата. Остальные назначения ниже описаны как целевая архитектура. Подключение хранилищ относится к среде запуска, политика хранения относится к организации, а место уже записанного артефакта определяется его индексом. [Конфигурация Core](core-config.md) · Профили хранения

## Выбор и полномочия

Владелец платформы подключает backend и определяет доступные назначения. Секреты подаются Core при старте. Администратор организации выбирает режим и срок для чата. Политика чата берётся на уровне организации, включая API и сигналинг. Выбор произвольного URL, пути или DSN из браузера или комнаты запрещён. Для остальных категорий единая модель выбора назначения и профилей комнат описана ниже как развитие.

В режиме `off` Core доставляет живые сообщения, очищает историю комнаты в памяти и прекращает экспорт через встроенные чат-вебхуки и анализ. Уже доставленные копии и очередь ранее отправленных событий живут по правилам своего назначения. `session` держит до 200 сообщений в памяти комнаты. `local` и `postgres` сохраняют историю для чтения после рестарта или закрытия комнаты. Один Core пишет в локальный том. Архивное чтение и запись используют текущий режим организации. При переключении прошлые данные остаются в прежнем хранилище до TTL. [Закрытая комната](../security/private-room.md) · [Конфиг организаций](../../apps/server/src/tenants.ts)

Для крупных артефактов индекс хранит tenant ID, room ID, stable ID, backend и непрозрачный ключ, размер, происхождение, состояние доступа/удаления, даты создания и истечения. Backend хранит оригиналы и производные. Ссылку формировать при выдаче с актуальной подписью. Метаданные можно держать локально даже при хранении байтов в S3. PostgreSQL для индекса выбирается независимо.

Core назначает каждой созданной встрече внутренний `room_instance_id` и сохраняет его в снимке комнаты. Повторное открытие того же `room_id` создаёт новый экземпляр с пустой историей. Пока встреча открыта, это правило действует и для участников, и для администраторского API. Когда комната закрыта, API администратора организации отдаёт историю одной встречи с наиболее свежими сохранёнными сообщениями. По этому API прежние встречи не объединяются. Полноценный каталог старых встреч с выбором экземпляра и отдельное управление удалением остаются следующими этапами.

## Миграция и выключение

1. **Подключить PostgreSQL только для долговременного чата.** Передать `AGIL_CHAT_POSTGRES_URL` как секрет Core. Для Helm можно использовать действующую настройку `postgres.injectEnv` и `AGIL_DATABASE_URL`. У роли БД должны быть права на нужную схему и таблицу. Core применяет идемпотентную миграцию автоматически. RAM-история не переносится. SQL исключает просроченные записи до физического удаления. При отказе БД запись не подтверждается и не рассылается, REST возвращает `503`, подключение к звонку остаётся доступным.
2. **Пилотировать смену назначения на одной категории и организации.** Сделать резервную копию, инвентаризировать ID, checksum, ACL, TTL и незавершённые операции. Повторный backfill сохраняет ID и не создаёт новые копии. После проверки целостности переключить назначение для новых записей. Старые артефакты читаются из их собственного маршрута до переноса или истечения.
3. **Закрыть окно конкурирующих записей.** Для переключаемой категории приостановить запись или вести единый журнал изменений с подтверждением двух сторон. Сверить ревизии, ACL и checksum. При откате согласовать сделанные после переключения изменения. Исходник очищается после приёмки и окончания согласованного окна отката.
4. **Разнести выключение и удаление.** Выключение блокирует новые записи и экспорт. Отдельное действие закрывает доступ к уже сохранённому и запускает очистку. Остановка экспорта отзывает ожидающие доставки. Для отключения БД сначала закрыть новые записи и завершить фоновые задачи. Если прежний архив должен оставаться доступным, сохранить подключение только для чтения или выполнить согласованный экспорт до удаления секрета. Удаление возобновляется после рестарта. Восстановление копии применяет журнал удалений до открытия доступа. Политика удаления · [Резервное копирование](../operations.md#7-backup-and-disaster-recovery)

## Эфиры и приватные встречи

Для публичного эфира используйте отдельное хранилище комментариев. OBS-брокер пишет их в локальный файл SQLite без внешней БД и выдаёт страницы по курсору. Медианоды раздают видео, а весь чат одного эфира обслуживает один брокер. Для нескольких брокеров понадобится общее хранилище комментариев, общие счётчики антиспама и доставка событий через общий канал. Если нужен вывод массового чата в Core-плеер Egress, подключите отдельный API комментариев к странице просмотра.

Для приватных встреч предлагаем оставить историю выключенной по умолчанию. Личное хранение включается явно на каждом устройстве и в пределах политики комнаты. Текст передаётся по защищённому каналу между участниками или шифруется на клиенте до отправки через посредника. Видеорежим P2P сам по себе защищённый чат не включает. Клиентское хранилище использует отдельный ключ встречи и срок для каждой записи. Истёкшее сообщение скрывается при открытии и удаляется фоновой очисткой, пока приложение работает. Кнопка «Очистить на этом устройстве» удаляет локальные записи и ключи. На других устройствах удаление выполняется по их собственной политике. Веб-приложение не может гарантировать физическое удаление в момент истечения, если браузер закрыт, и не управляет сделанными копиями или снимками экрана. Клиентское хранилище остаётся проектом до проверки шифрования, обмена ключами и запрета серверного экспорта.

## План QA

| Путь | Проверяемый результат |
|---|---|
| Core без БД | Без DSN создать комнату и использовать `off` и `session`. Проверить отсутствие SQL-подключения, пустую историю при `off` и исчезновение RAM-истории по закрытии комнаты. |
| PostgreSQL только для чата | Рестарт между записью и повтором оставляет один scoped ID. Проверить в хранилище два tenant с одинаковым room ID. Каждый читает только свои данные. Срок исключает запись из API до фонового удаления. База недоступна без записи в резервный backend. Существующая схема повторно проходит старт. |
| Файл и медиа | Остановить процесс между загрузкой и публикацией. Проверить восстановление без потери ACL, очистку временных файлов и карантина, действующую подпись и отзыв старой ссылки при удалении, очистку сегментов HLS. |
| Субтитры, заметки и экспорт | Выключить сохранение посреди звонка. Проверить живую доставку, отсутствие новых сохранённых сегментов и отдельный purge прежних. Проверить кэш перевода, вложенную расшифровку, webhook и внешний процессор. |
| Перенос и удаление | Повторить backfill и сверку, остановить перенос, вернуть прежний маршрут и сохранить изменения, произошедшие после переключения. Проверить истечение, прерванную очистку, недоступное хранилище и изолированное восстановление копии. |
