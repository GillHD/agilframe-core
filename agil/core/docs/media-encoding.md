# Кодирование видео: камера → аппаратный кодек → программный fallback

Политика AgilFrame: **сервер не транскодирует видео обычных звонков**. Мы
максимально используем то, что уже умеет устройство/браузер, затем аппаратный
кодер, и только потом программный. Это экономит CPU/GPU сервера и снижает
задержку.

## 1. Что реально можно взять «готовым» с камеры

В браузере `getUserMedia()` отдаёт **сырые кадры** (I420/NV12), а не готовый
H.264/H.265/AV1-битстрим: производители камер и ОС не отдают приложениям
закодированный поток через MediaStream. Поэтому «взять уже закодированное видео
с камеры» в веб-приложении нельзя; можно:

1. **Выбрать кодек, который устройство/браузер кодирует аппаратно** (H.264,
   AV1, VP9, VP8) — WebRTC-стек сам использует аппаратный энкодер, если он
   доступен для выбранного кодека.
2. **Задать порядок предпочтений** (`video.encoding.preferredCodecs`):
   AV1 → H.264 → VP9 → VP8 (по умолчанию). Chrome поддерживает H.265 в
   WebRTC с версии 136 на совместимых устройствах. Встроенный виджет
   AgilFrame исключает его из согласования. [Chrome 136](https://developer.chrome.com/release-notes/136#h265_hevc_codec_support_in_webrtc).
3. **Попросить аппаратный энкодер** (`video.encoding.strategy='prefer-hardware'`):
   браузер выбирает hardware, если может; иначе — software.
4. **Не транскодировать на сервере**: SFU (LiveKit) только пересылает выбранный
   кодек; при несовместимости подписчика используется simulcast/слой, а не
   серверный transcode.

## 2. Приоритеты

| Приоритет | Что | Где |
|---|---|---|
| 1 | Кодек, который камера/браузер умеет аппаратно (H.264/AV1/VP9) | клиент |
| 2 | Аппаратный энкодер браузера/ОС | клиент |
| 3 | Программный энкодер (VP8/VP9/H.264 baseline) | клиент |
| 4 | Серверный transcode | **только opt-in**, по умолчанию запрещён |

## 3. Настройки

```jsonc
"video": {
  "codecs": ["av1", "h264", "vp9", "vp8"],
  "preferredCodec": "h264",
  "encoding": {
    "strategy": "auto",                 // auto | prefer-hardware | software-only
    "preferredCodecs": ["av1", "h264", "vp9", "vp8"],
    "allowH265": false
  },
  "simulcast": true,
  "scalableVideoCoding": true,
  "degradationPreference": "maintain-framerate"
}
```

- `video.codecs` определяет список включённых видеокодеков камеры. В обычном режиме сначала рассматриваются включённые кодеки из `video.encoding.preferredCodecs`, затем остальные включённые кодеки. Для старой конфигурации без пригодного списка приоритетов первым пробуется включённый `video.preferredCodec`.
- `auto` использует этот порядок. Браузер и медиастек выбирают реализацию кодека.
- `prefer-hardware` поднимает в списке поддерживаемые WebRTC-кодеки, для которых браузер сообщает энергоэффективное кодирование и декодирование при заданном профиле камеры. За ними идут кодеки с энергоэффективным кодированием. В каждой группе сохраняется порядок организации. При отсутствии данных сохраняется исходный порядок. [Media Capabilities](https://www.w3.org/TR/media-capabilities/).
- `software-only` сохраняется как имя режима в API. В редакторе это «Приоритет совместимости». Порядок включённых кодеков в этом режиме начинается с VP8 и H.264. Браузер может использовать для них аппаратное кодирование.
- Если локальный браузер не поддерживает включённые кодеки, mesh использует его доступные кодеки без H.265, а SFU использует выбор LiveKit по умолчанию. Для E2EE действует отдельное правило SFU с VP8.

## 4. Баланс качества и надёжности

- **Simulcast и SVC** позволяют получателю выбрать разрешение в пределах
  опубликованных слоёв без транскодирования на сервере. Для камеры в LiveKit
  с VP9 или AV1 параметр `video.scalableVideoCoding` включает SVC в режиме
  `L3T3_KEY` и отключает simulcast. При выключенном SVC клиент запрашивает
  `L1T1`, а simulcast следует отдельной настройке `video.simulcast`.
  Доступность нескольких независимых кодирований зависит от браузера и SDK.
  Для VP8 и H.264 применяется настройка simulcast.
- **Degradation preference**: `maintain-framerate` для речи/лиц,
  `maintain-resolution` для текста/демонстрации экрана.
- **Adaptive stream/dynacast** в SFU: подписка только на нужные слои.
- **Fallback**: при деградации — снижение разрешения/FPS → аудио-режим → чат
  (fallback.lowBandwidth), без серверной обработки.
- **Ограничения**: `maxResolution`, `maxFps`, `maxBitrateKbps`,
  `keyFrameIntervalMs`.
- Настройки звонка показывают предпочтительный кодек и оценку поддержки ускорения. Реальную реализацию текущего потока проверяют отдельно по WebRTC-статистике.

## 5. Как это реализуется в клиенте

В прямом звонке `audio.codecs` задаёт рекомендуемый набор, а
`audio.preferredCodec` ставит выбранный основной кодек первым в
`setCodecPreferences()`. При наличии Opus виджет объявляет включённый RED
в SDP, если его поддерживает браузер. При отсутствии совместимых основных
кодеков на устройстве используются настройки браузера. Битрейт Opus не
применяется к PCMU или G.722. В SFU аудиокодеком управляет медиастек.

1. `RTCRtpSender.getCapabilities('video')` → список поддерживаемых кодеков.
2. Отфильтровать по `preferredCodecs`; H.265 игнорируется.
3. `RTCRtpTransceiver.setCodecPreferences()` — порядок для SDP.
4. Для SFU: `RoomOptions.publishDefaults.videoCodec` = первый поддерживаемый;
   `simulcast`, `dynacast`, `adaptiveStream`.
5. `navigator.mediaCapabilities.encodingInfo()` и `decodingInfo()` с `type: 'webrtc'` оценивают профиль при настройке кодека. Ожидание подсказки ограничено 250 мс. [Media Capabilities](https://www.w3.org/TR/media-capabilities/).
6. В активном звонке снимите `RTCPeerConnection.getStats()` дважды и выберите потоки с приростом `framesEncoded` или `framesDecoded`. Сопоставьте `codecId` с `mimeType`. Для отправки запишите `encoderImplementation` и `powerEfficientEncoder`, для приёма — `decoderImplementation` и `powerEfficientDecoder`. Браузер может скрывать эти поля. [WebRTC Stats](https://www.w3.org/TR/webrtc-stats/).

```sh
node agil/core/qa/widget/sfu-checks.mjs --hardware-only --hardware-headed
```

Этот сценарий запускает локальный Core, LiveKit и два профиля Chrome без отключения GPU. Он проверяет активные потоки для автоматического порядка кодеков, H.264 с simulcast, H.264 с одним слоем и прямого звонка. Отчёт находится в `.tmp/webrtc-hardware/sfu-qa.json` либо в `AGIL_QA_OUTPUT_DIR`.

На физическом Redmi Note 8T в локальном прямом звонке H.264 кодировался через `NdkVideoEncodeAccelerator(OMX.qcom.video.encoder.avc)` при 720×1280 и декодировался через `MediaCodecVideoDecoder` при 640×360. Обе дорожки показали `powerEfficient=true` на обработанных кадрах. Для повтора запустите Android QA с `--codec-stats`. Сценарий Android.

На Windows с RTX 3060 в видимом Chrome измерены следующие активные пути на локальном Core и LiveKit 1.13.11. Тестовая камера даёт воспроизводимый исходный кадр, а кодирование и декодирование выполняет браузер.

| Режим | Кодирование | Декодирование |
|---|---|---|
| Прямой звонок, H.264 720p | NVIDIA H.264 Encoder MFT, аппаратное | D3D11 Video Decoder, аппаратное |
| SFU, H.264 simulcast | OpenH264 на опубликованных слоях, программное | D3D11 Video Decoder, аппаратное |
| SFU, H.264 одним слоем 720p | OpenH264, программное | D3D11 Video Decoder, аппаратное |
| SFU, автоматический порядок на этом ПК | AV1 через `libaom`, программное | AV1 через `dav1d`, программное после попытки D3D11 |

Однослойный SFU повторён при вручную выбранном высоком качестве и отключённой адаптации к слабой связи. При 1280×720 на обоих клиентах результат кодирования остался программным. Сценарий Chromium.

Причину проверили отдельно. При одинаковых 720p и `packetization-mode=1` штатный LiveKit согласовал профиль `42e01f`, а прямой звонок согласовал `42001f`. На отдельном локальном LiveKit ограничили H.264 профилем `42001f`. Однослойный SFU после этого согласовал `42001f` и использовал NVIDIA H.264 Encoder MFT на обоих клиентах. D3D11 декодировал входящее 720p аппаратно. Профиль общего SFU на embedded call не менялся. [Настройка `fmtp_line` в LiveKit](https://github.com/livekit/livekit/blob/master/pkg/config/config.go).

С этим же профилем при simulcast активны слои 160×90, 320×180 и 1280×720. На обоих отправителях WebRTC показал смешанный адаптер из двух OpenH264 и одного NVIDIA H.264 Encoder MFT. Наличие аппаратного пути подтверждено, ускорение каждого слоя отдельно требует своей проверки. В одном объединённом прогоне после SFU один исходящий поток прямого звонка не запустился. В отдельном сравнительном прогоне прямой звонок подтвердил аппаратное кодирование и декодирование с обеих сторон.

```sh
node agil/core/qa/widget/sfu-checks.mjs --hardware-only --hardware-headed --single-layer-only --h264-baseline-sfu
```

Для совместной проверки simulcast и одного слоя уберите `--single-layer-only` и добавьте `--require-hardware`. Проверка требует хотя бы один активный поток с `powerEfficient=true` в каждом направлении на обоих клиентах. Для simulcast успешный результат допускает смешанный адаптер.

Для отдельной матрицы VP8, VP9 и AV1 используйте один кодек на комнату. Второй запуск повторяет VP9 и AV1 через SFU с отключённым SVC.

Оба клиента Chrome на RTX 3060 передали и приняли активные кадры во всех восьми сценариях. Аппаратный декодер в таблице означает `ExternalDecoder (D3D11VideoDecoder)` с `powerEfficientDecoder=true`.

| Кодек | Кодирование в прямом звонке и SFU | Декодирование в прямом звонке | Декодирование через SFU |
|---|---|---|---|
| VP8 | `libvpx`, программное | `libvpx`, программное | `libvpx`, программное при simulcast |
| VP9 | `libvpx`, программное | Аппаратное | С SVC `L3T3_KEY` программное через `libvpx`. Без SVC аппаратное при 1280×720 |
| AV1 | `libaom`, программное | Аппаратное | С SVC `L3T3_KEY` программное через `dav1d`. Без SVC аппаратное при 1280×720 |

На Redmi Note 8T прямой звонок VP8 использовал аппаратный `OMX.qcom.video.encoder.vp8` на 720×1280 и аппаратный MediaCodec на 640×360. VP9 использовал программный `libvpx` на отправке и аппаратный MediaCodec на приёме. При запросе AV1 двусторонний звонок согласовал H.264. Android WebView объявил AV1 в списке кодеков приёмника. В списке кодеков отправителя его не было. Сценарий Android.

Отдельная односторонняя пара Chrome → Redmi подтвердила приём AV1. WebView декодировал 12 кадров 320×180 через программный `dav1d`, `powerEfficientDecoder=false`. Проверка запускается с флагом `--av1-receive` в Android QA. Сценарий Android.

```sh
node agil/core/qa/widget/sfu-checks.mjs --hardware-only --hardware-headed --other-codecs
node agil/core/qa/widget/sfu-checks.mjs --hardware-only --hardware-headed --other-codecs --single-layer-only
```

### Дополнительные проверки H.265 и аудио

На Windows с RTX 3060 и Chrome 157 прямое соединение между двумя
`RTCPeerConnection` вне виджета передало и декодировало более 30 кадров H.265
при источнике 1280×720. Кодер — `NVIDIA HEVC Encoder MFT`, декодер — `D3D11VideoDecoder`.
Оба показали `powerEfficient=true`. В тех же условиях при
`allowH265=true` H.265 отсутствовал и в предложении, и в ответе SDP
встроенного виджета. Поддержка H.265 через LiveKit и Android WebView в этом
прогоне не проверялась.

В четырёх прямых звонках через виджет на Chrome 157 проверили фактические
кодеки входящих и исходящих аудиопакетов у обоих участников.

| Конфигурация | Результат |
|---|---|
| Opus | Пакеты Opus в обе стороны |
| Opus + RED | RED указан в SDP обеих сторон, активные пакеты — Opus |
| PCMU (G.711 μ-law) | Пакеты PCMU в обе стороны |
| G.722 | Пакеты G.722 в обе стороны |

## 6. Сервер

- Обычный звонок: только signaling/чат/присутствие; медиа — P2P (mesh) или
  SFU-пересылка. **Никакого decode/encode/blur/transcode на сервере.**
- SFU (LiveKit): пересылает RTP; не транскодирует.
- Egress/запись/RTMP/HLS: отдельный opt-in (`mediaProcessing.egress`), требует
  CPU/GPU и выключен по умолчанию.
- Проверка: `GET /v1/admin/media/processing` → `serverProcessingActive=false`,
  `sfuForwardingOnly=true` при SFU.

## 7. Ограничения

- Браузер не даёт «готовый encoded stream» с камеры; см. §1.
- Встроенный виджет согласует H.264, VP8, VP9 и AV1. Флаг `allowH265` не добавляет H.265 в его SDP.
- Аппаратный энкодер может быть занят другими приложениями — тогда fallback
  software, качество/CPU меняются.
- Реальный выбор кодека зависит от браузера, ОС и получателя; наша политика —
  приоритеты, а не жёсткая гарантия.
- Серверный transcode не реализован (только каркас egress); при включении
  потребуется отдельный пул воркеров.
