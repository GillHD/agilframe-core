# Интеграция в компанию

Маршрут B2B-пилота от создания организации и первого закрытого звонка до записи, эфиров, уведомлений и эксплуатации.

## [onboarding] Организация и токены

1. Оператор поднимает Core за HTTPS и WSS, задаёт `AGIL_PUBLIC_ORIGIN`, ограничивает доступ к административным маршрутам и передаёт секреты через окружение или хранилище секретов. Для закрытого контура задайте `AGIL_ALLOW_ANONYMOUS=0`. Проверьте `GET /v1/ready` и открытие WebSocket на `/ws`. [Развёртывание](/docs/deployment.md) · [Границы API](/docs/api-exposure.md)
2. Владелец платформы создаёт отдельную организацию для пилота через `POST /v1/admin/tenants`. В заголовке `x-api-key` передаётся платформенный ключ. Пример тела — `{"tenantId":"acme-pilot","name":"Acme Pilot","preset":"corporate"}`. Ответ содержит `tenant`, `apiKey` и `embedUrl`. Запишите `apiKey` в хранилище секретов бэкенда компании сразу после получения. `POST /v1/admin/tenants/{tenantId}/keys` сразу заменяет предыдущий динамический ключ. Перед ротацией согласуйте переключение интеграций. [Организации и ключи](/docs/saas.md)
3. Бэкенд компании проверяет сессию сотрудника и его доступ к конкретной встрече. Затем он создаёт комнату и выдаёт персональный токен с корпоративным `participantId`. Браузеру передаются только данные подключения этого участника.

| Данные доступа | Кто хранит и использует |
| --- | --- |
| Платформенный `AGIL_PLATFORM_KEY` | Оператор платформы, `x-api-key` для создания организаций и управления их ключами. |
| API-ключ организации | Бэкенд компании, `x-api-key` для комнат, токенов, конфигурации и административных операций своей организации. |
| Join-токен | Клиент сотрудника. Привязан к организации, комнате, роли и участнику. Передаётся в SDK или как `Authorization: Bearer` для операций участника. Для ссылок с токеном исключите сохранение URL в аналитике и общих журналах. |
| OIDC и SCIM | Администратор IdP и оператор Core. OIDC использует отдельный секрет приложения, SCIM — `AGIL_SCIM_TOKEN` и `x-tenant-id`. |
| Enrollment, MCP, медиаключи | Храните отдельно. Ключ регистрации ноды, Bearer HTTP MCP, ключ публикации эфира и подписанная playback-ссылка имеют разные назначения. |

## [first-call] Первый закрытый звонок

Запросы ниже выполняются с бэкенда компании. `$CORE` — origin Core, `$TENANT_KEY` — ключ организации. `staff-101` и `staff-202` здесь тестовые идентификаторы. В продукте список определяется проверенным составом встречи, а ID, имя и роль определяет бэкенд после проверки сессии.

```bash
curl --fail-with-body -X POST "$CORE/v1/rooms" \
  -H "x-api-key: $TENANT_KEY" -H 'content-type: application/json' \
  -d '{"tenantId":"acme-pilot","name":"Пилот Acme","mode":"group","allowedParticipantIds":["staff-101","staff-202"]}'
```

Подставьте `room.id` из ответа в переменную `$ROOM`. Выпустите отдельный токен для каждого сотрудника. В API время жизни токена задаётся в секундах. Пример использует пять минут на вход.

```bash
curl --fail-with-body -X POST "$CORE/v1/tokens" \
  -H "x-api-key: $TENANT_KEY" -H 'content-type: application/json' \
  -d "{\"tenantId\":\"acme-pilot\",\"roomId\":\"$ROOM\",\"participant\":{\"participantId\":\"staff-101\",\"name\":\"Анна\",\"role\":\"host\"},\"ttlSec\":300}"
```

Клиент компании получает `roomId`, `token`, `expiresAt` и `permissions`. Подключите виджет на странице, загрузив `/sdk/agilframe.js` с Core. Добавьте точный origin страницы в `integrations.allowedOrigins` и проверьте HTTPS и WebSocket с этого origin.

```js
const call = await AgilFrame.mount('#call', {
  serverUrl: coreOrigin,
  tenantId: 'acme-pilot',
  room: join.roomId,
  token: join.token
});
```

Для своего интерфейса используйте состояние и методы SDK. Для быстрого пилота можно использовать iframe или экран WebView. При обновлении допуска приложение компании снова проверяет сессию и членство комнаты. Проверьте вход двух участников, отсутствие допуска у третьего, запрет токена другой комнаты и истёкшего токена, а также отличия действий `host` и `guest`. [Контракт SDK](/docs/sdk.md) · [Интеграция с мессенджером](/docs/messenger.md)

## [access-and-ui] Доступ, конфигурация и интерфейс

| --- | --- | --- |
| Роли, вход и модерация | `GET/PUT /v1/admin/access-policy`, `GET/POST /v1/admin/roles`, `PUT/DELETE /v1/admin/roles/{id}`. Для своей роли укажите `participant.roleId` при выдаче токена. Модерация через лобби, `/v1/admin/rooms/{roomId}/lock` и `/kick`. | Исключите сотрудника из выдачи токенов на бэкенде. Проверьте выдачу, вход и серверный отказ на запрещённое действие. [Роли](/docs/roles.md) |
| Бренд и функции | `GET/PATCH /v1/tenants/{tenantId}/config`. Настройте `branding`, `theme`, `layout`, `features` и разрешённые origin. Обычный `PATCH` обновляет нужные поля. Для публикации полного черновика используйте `editorDraft` и `baseEtag` из чтения конфигурации. При `409 config_conflict` перечитайте конфиг и перенесите изменение. | Проверьте новое чтение и звонок вне предпросмотра. Пройдите светлую, тёмную и системную темы. Импорт и экспорт в панели используют чтение и запись того же конфига. [Редактор](/wiki/setup.html#editor) · [Резервная копия](/wiki/setup.html#configuration-backup) |
| Форматы комнат | `POST /v1/rooms` принимает `mode`, `transport` для direct и `configOverrides`. WebSDK компилирует версионированный профиль на бэкенде компании. Профиль SFU требует настроенной медиаплоскости организации. | Проверьте direct P2P в аудиорежиме с подтверждаемым переходом в видео и group SFU. Сверьте фактический `mediaMode` и вместимость из ответа. [Профили и SDK](/docs/sdk.md) |
| Постоянные голосовые каналы | `GET/POST /v1/admin/voice-channels`, `PATCH /v1/admin/voice-channels/{channelId}` для состава, `POST /v1/admin/voice-channels/{channelId}/join` для персонального допуска. | Пользователь из состава входит, исключённый не получает новый допуск. Клиент запрашивает актуальные `roomId` и токен при повторном входе. [Голосовые каналы](/docs/voice-channels.md) |
| Звонок и совместная работа | Камера, микрофон, выбор устройств, фон, демонстрация, доска и реакции работают через клиент, SDK и сигналинг. Опросы, лобби и подкомнаты имеют room REST-маршруты. Чат и загрузки доступны через room API, SDK или WS по типу действия. | Проверьте два клиента с разными ролями, получение файла и сообщения, голосование и возврат из подкомнаты. Подтверждение захвата и разрешения устройств выдаёт пользователь в браузере или ОС. [Встречи](/wiki/#daily) · [Справочник REST и WS](/docs/api.md) |

**Пример: включить запись у организации с профилем `corporate`.** Этот профиль выключает запись при создании. Отправьте частичное обновление с ключом организации.

```bash
curl --fail-with-body -X PATCH "$CORE/v1/tenants/acme-pilot/config" \
  -H "x-api-key: $TENANT_KEY" -H 'content-type: application/json' \
  -d '{"features":{"recording":true},"session":{"recording":{"enabled":true}}}'
```

Прочитайте настройки тем же API, проверьте право `recording` для нужной роли и создайте комнату для проверки. Для серверной записи дополнительно разверните и настройте Egress. Для отдельной комнаты передайте тот же фрагмент в `configOverrides` при её создании.

## [api-gaps] Что осталось для управления из системы компании

1. **Сервисные credentials.** Для текущего пилота ключ организации остаётся на бэкенде. Для нескольких независимых коннекторов нужен выпуск, список, ограничение по операциям, отзыв и ротация независимых сервисных ключей организации. Для SCIM в общем контуре отдельно нужны tenant-scoped credentials. Внешним агентам нужен делегированный временный доступ на правах пользователя и с разрешённым подмножеством операций.
2. **Жизненный цикл доступа.** Закрытый список сейчас задаётся при создании комнаты. Для изменения состава активной встречи нужен API изменения allowlist с описанным поведением уже подключённых участников и выданных токенов. До этого бэкенд прекращает выдачу новых токенов и использует штатные lock/kick там, где требуется.
3. **Конкурентные записи и повторные запросы.** Версия конфигурации защищает публикацию `editorDraft`. Для нескольких сервисов, меняющих обычный `PATCH` или `PUT`, нужен общий условный контракт записи. Добавить проверяемые правила повторного создания комнат и ротации credentials. Для Egress действует отдельная идемпотентность запуска.
4. **Эфиры и расширения.** Для единого управления комнатами и независимыми публичными эфирами нужен стабильный tenant API на жизненный цикл публикации, ключи, модерирование и повторы. Профили комнат сейчас принадлежат интегратору. Реестр версий на стороне Core имеет смысл, если разные приложения должны получать одинаковые опубликованные профили.
5. **Состояние и OpenAPI.** В OpenAPI описывать не только переключатель, но и режим авторизации, ошибки конфликта, фактическую готовность зависимости, чёткую область токена и асинхронные события. Генерацию клиента сверять с серверными тестами. Публичный контракт и полный административный контракт имеют разные условия доступа. [Справочник API](/docs/) · [Публичная OpenAPI](/openapi.json)

## [acceptance] Приёмка пилота

1. Создайте две тестовые организации. Подтвердите, что ключ первой не читает или не изменяет закрытые данные второй. Секреты и полный токен не попадают в сохранённые логи.
2. Встройте звонок в реальное приложение компании. Проверьте роли, длительность токена, повторный вход, браузерные разрешения, мобильный вид и применение конфига за пределами редактора.
3. Подключайте внешние сервисы по одному. Для каждого запишите версию, операцию настройки, роль, ожидаемый результат и подтверждение на принимающей стороне. Отдельно подтвердите запись и её архив, SSO, STT, SIP и TURN между независимыми сетями, если они входят в этот пилот.
4. Передайте компании ссылки на Wiki и OpenAPI, список её операций и ответственных за секреты, DNS, файлы и инциденты. Для правок Wiki используйте «Wiki» в платформенной панели.
