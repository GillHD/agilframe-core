# Планы развития медиа

AgilFrame должен позволять строить приложения с собственным интерфейсом поверх общего медиа-движка. Два ориентира для проверки архитектуры — публичный эфир с чатом и голосовые каналы сообщества. Сценарии, для которых ещё нет сквозной приёмки, перечислены ниже.

## Публичный эфир в духе Twitch

- [ ] Организатор создаёт канал или эфир, получает отдельный адрес и ключ для OBS и может отозвать ключ. Ведущий публикует по RTMPS или WHIP. Зритель открывает тот же эфир через HLS или WHEP, в зависимости от выбранного режима. За основу берём существующее [демо OBS](../deploy/obs-demo/README.md).
- [ ] Браузер проигрывает эфир и показывает чат с отдельными правами зрителя и модератора. Режимы публичного и закрытого просмотра проверяются отдельно. Публикация, просмотр и управление эфиром используют разные разрешения.
- [ ] После базового сценария добавить несколько профилей HLS, CDN, запись и повторы. Приёмка включает задержку от источника до плеера, переход между профилями и восстановление воспроизведения.

## Голосовые каналы в духе Discord

- [x] Реестр закрытых каналов хранит состав и роли организации. Корпоративный сервер выдаёт доступ к комнате участника по его стабильному идентификатору. Проверены изоляция организаций, отзыв комнаты при изменении состава, повторная выдача после перезапуска и переключение лидера Core. [Настройка голосовых каналов](voice-channels.md)
- [ ] Сервер компании назначает участников и роли для постоянных каналов. SDK предоставляет создание интерфейса, подключение к голосу, переключение каналов, камеру, демонстрацию экрана и индикацию говорящих.
- [ ] При переключении каналов звук предыдущего канала прекращается, звук нового начинается без пересечения. Переподключение восстанавливает права и идентичность. Разговоры разных каналов и организаций изолированы. Текстовые каналы, присутствие вне звонка и история сообщений требуют собственного контракта продукта.

## Кастомные медиапайплайны

Текущие правила уже направляют Edge в комнату и запускают выходы комнаты в RTMP, HLS и запись. Серверные тесты подтверждают выбор правила, разветвление на несколько выходов и повторный вызов без дублирования задачи. Эти правила можно использовать как основу общего контракта маршрутизации. [Тесты маршрутизации](../apps/server/test/routing.test.ts)

- [ ] Начать с декларативных конфигураций: источник, необязательная обработка, один или несколько явно заданных выходов. Первый сквозной сценарий — один вход OBS и два выхода для разных зрительских режимов. Зафиксировать таблицу совместимости протоколов и кодеков, условия ретрансляции без перекодирования и случаи, где нужен отдельный транскодер.
- [ ] Core назначает здоровый узел приёма по возможностям и ёмкости. Источник передаёт медиа напрямую на назначенный узел. Плеер получает адрес доступного узла просмотра по выбранной политике задержки и загрузки. Запланировать проверку отказа узла, переподключения источника и восстановления зрителя.
- [ ] Для каждого выхода определить полномочия, срок жизни, статус и причину сбоя. Приёмка охватывает повтор запуска, остановку и освобождение ресурсов, отказ одного выхода при работающих остальных и отклонение несовместимой конфигурации до запуска.
- [ ] Будущая опция — обработка кадров на клиенте или на серверном воркере через OpenCV либо нейросетевую модель. Определить, где доступны декодированные кадры, какой эффект остаётся локальным, а какой меняет поток для зрителей. Для серверной обработки задать ограничения CPU/GPU и задержки, требования к согласию и совместимости со сквозным шифрованием, поведение при недоступном воркере. При выключенной обработке базовые маршруты должны работать без этой зависимости.

### Внешние медиавходы

| Вход | Область применения | Что проверить при подключении к AGIL |
| --- | --- | --- |
| RTP/UDP из GStreamer | Оборудование и обработчики в частной сети | Выдачу адреса приёма, описание дорожек через SDP, H.264 и аудио отдельно, потерю пакетов и повторный пуск |
| RTSP | Камеры, регистраторы и GStreamer | Получение потока по заданному адресу и прямую публикацию от клиента. Отдельно проверить TCP, авторизацию камеры и восстановление после обрыва |
| SRT с MPEG-TS | Публикация через нестабильный канал | Входящий поток с H.264/AAC, защиту доступа, восстановление после потери пакетов и задержку |
| UDP с MPEG-TS | Шлюзы и оборудование в частной сети | Ограничение сети источника, состав программ и дорожек, совместимость с выходом HLS |
| HLS как внешний источник | Подключение уже опубликованного эфира | Проверку разрешённых источников, переключение вариантов и обновление истекающих ссылок |

RTP, RTSP и SRT — транспорты. Профиль кодека и контейнер задаются отдельно. Первый браузерный выход для камер и шлюзов — HLS с H.264/AAC. Для низкой задержки проверяем WHEP отдельной матрицей кодеков. Raw RTP следует принимать на выделенном интерфейсе в доверенной сети. Управляемая выдача входов и секретов из AGIL остаётся отдельной задачей. [MediaMTX и GStreamer](https://mediamtx.org/docs/publish/gstreamer) · [SRT](https://mediamtx.org/docs/publish/srt-clients)

### Управляемые пайплайны на Edge

В Core уже есть [Flows](flows.md) с типизированными источниками, обработчиками, выходами и статусами отдельных ветвей. Часть источников описана со статусом `pending`. Для Edge предлагается расширить этот контракт и добавить исполнение через `node-agent`.

1. **Профиль.** Пользователь выбирает источник, необязательные шаги обработки и выходы. Версия профиля фиксирует протокол и направление входа (push или pull), дорожки и кодеки, правила доступа, ссылки на секреты и допустимые преобразования. Например, RTSP-камера с H.264/AAC может дать HLS без перекодирования, а для WHEP той же камеры аудио можно преобразовать в Opus. Проверка совместимости до запуска должна показывать, что именно требуется для каждого выхода.
2. **Назначение.** Core проверяет права организации и выбирает здоровый Edge с нужными протоколами, кодеками, свободными портами и ресурсами. Для push Core возвращает адрес назначенного узла и короткоживущий ключ, если протокол поддерживает аутентификацию. Для RTP в доверенной сети резервируется порт и выдаётся SDP. Для pull Edge получает разрешённый адрес и доступ к секрету на срок задания. Права на публикацию и просмотр выдаются отдельно.
3. **Исполнение.** `node-agent` запускает изолированный воркер, следит за лимитами и сообщает Core, запущен ли вход, появились ли медиаданные и какие выходы работают. Core хранит привязку запуска к узлу и номер назначения. Повторный запуск с тем же ключом не дублирует процесс, отчёты от прежнего узла после переназначения отклоняются. При остановке освобождаются порты и ресурсы. При отказе push-узла издателю может потребоваться переподключение.
4. **Доставка.** Медиа идёт напрямую на Edge. Для просмотра на другом узле поток передаётся между Edge по мере появления зрителей. Core выдаёт адрес просмотра по политике задержки, нагрузки или их сочетания. Ошибка записи или одного выхода отображается отдельно и не останавливает исправные ветви.

| Компонент | Роль на Edge |
| --- | --- |
| [MediaMTX](https://mediamtx.org/docs/publish/gstreamer) | Приём RTP, RTSP и SRT, ретрансляция и переупаковка дорожек, когда кодеки совместимы с выходом. |
| [LiveKit Ingress](https://docs.livekit.io/transport/self-hosting/ingress/) | Публикация внешнего источника в комнату SFU. Отдельно проверить транскодирование RTMP и режим WHIP с передачей совместимых дорожек. |
| [FFmpeg](https://ffmpeg.org/ffmpeg.html#Streamcopy) | Переупаковка, файловые задачи и преобразование отдельных дорожек. `streamcopy` сохраняет сжатый поток и экономит ресурсы. |
| [GStreamer](https://gstreamer.freedesktop.org/documentation/application-development/basics/elements.html) | Долгоживущий граф с ветвлением, обработкой кадров и адаптерами оборудования. Изолировать буферы ветвей и передавать ошибки и переходы состояния воркеру через [GstBus](https://gstreamer.freedesktop.org/documentation/application-development/basics/bus.html). |

API организации принимает структурированный профиль и имена доступных шагов. Воркеры собирают аргументы FFmpeg или граф GStreamer из проверенных параметров. Для собственного развёртывания администратор платформы может подключать проверенные модули с описанием входов, выходов и требуемых ресурсов. Воркеры ограничивают доступ к файлам, входящим портам и исходящим адресам. Проверка ограничений необходима и при разрешении DNS, и при переподключении по внешней ссылке.

Порядок реализации и приёмки:

1. Подключить RTSP pull и RTP push к Flows через `node-agent`. Проверить назначение узла, HLS с видео и звуком, повтор запуска, закрытие порта после остановки и изоляцию двух организаций.
2. Добавить SRT и выход WHEP. Проверить выбор узла зрителя, передачу между узлами и восстановление после обрыва. По каждому режиму отдельно измерить задержку от источника до браузера.
3. Добавить профили перекодирования и расширяемые шаги FFmpeg/GStreamer. Для аппаратного кодирования и декодирования фиксировать фактическую реализацию, выбранную воркером, и отдельно проверять программный путь. OpenCV и модели подключать отдельными шагами после проверки задержки и лимитов.

Локальный тест подтвердил H.264 и AAC в браузере через HLS для RTP/UDP, MPEG-TS/UDP, RTSP и шифрованного SRT. Для выхода WHEP шифрованный SRT передал в Chromium H.264 и Opus. Управляемый запуск через Edge, синхронизация A/V через raw RTP и межузловая доставка остаются на приёмке. Для RTSP-профиля следует явно указывать упаковку AAC в RTP. Проверенная связка с HLS использует `MPEG4-GENERIC`. Журнал проверки · [Форматы медиавходов](/wiki/index.html#input-formats)

### Маршруты из звонка, браузера и OBS

- Комната со звуком и демонстрацией экрана → Egress → HLS/CDN. Ведущие остаются в комнате, зрители используют плеер. Проверить компоновку демонстрации и слышимость участников и звука вкладки в одном эфире на целевом Egress.
- OBS, игровой энкодер или обработчик → WHIP, SRT или RTP → Edge → WHEP. Для одной публикации с двумя выходами подбирать дорожки под каждый выход, сохраняя совместимое сжатое видео. Локальный RTP с H.264/Opus уже дошёл до WHEP-плеера AGIL.
- Отдельная публикация экрана из браузера в эфир → WHIP без входа в комнату. Нужны выданный организатору ключ, выбор экрана и звука в диалоге браузера, предварительный просмотр, остановка при отзыве захвата и освобождение сессии. Сейчас для демонстрации из браузера доступен маршрут через комнату и Egress.

Выбор HLS или WHEP уже сохраняется в настройках организации. Автоматическое назначение источника и настройку медиаобработки следует связать с исполнением Flows. [Инструкция Wiki](/wiki/index.html#stream-routing) · [Интерфейс для разработчика](/docs/api.md)

### Тренинги и презентации

- Ведущие подключаются в SFU-комнату через WebRTC. Демонстрация экрана публикуется там же и остаётся интерактивной. Внешняя аудитория получает отдельный HLS-выход комнаты через Egress/CDN. Переход между экраном и камерами проверяется в композитном эфире.
- Чат зрителей и очередь вопросов должны работать на странице просмотра с отдельным разрешением на чтение и отправку. Допуск в чат не занимает место в комнате и не выдаёт право подключаться к WebRTC. Ведущие видят вопросы в комнате, модераторы могут скрывать сообщения и отключать отправку. Приёмка охватывает изоляцию организации и эфира, истечение допуска, лимиты отправки и отключение чата по окончании тренинга.

## План настраиваемых типов комнат

Один тип описывает возможности комнаты и связи между ними. Например, «Тренинг» включает групповую комнату для ведущих, демонстрацию экрана, HLS-выход и вопросы зрителей. Из одного типа организатор создаёт несколько независимых событий. Сервер хранит версию типа, по которой создано каждое событие.

### Что переиспользовать

| Часть | Что уже есть | Что добавить |
| --- | --- | --- |
| Комната и доступ | `direct` и `group`, выбор транспорта, роли и `configOverrides` | Идентификатор и версия опубликованного типа, проверка совместимости компонентов при создании комнаты |
| Внешний вид | Темы, элементы управления SDK и `ui: 'headless'` | Описание доступных компонентов и их мест в стандартной раскладке. Манифест для собственного интерфейса |
| Видеомаршруты | [Flows](flows.md), Egress и проверенные входы через MediaMTX | Привязка плана маршрутов к конкретной комнате, запуск и статус каждого выхода |
| Вопросы аудитории | Чат звонка, корпоративные роли и REST-отправка | Допуск зрителя с правами на чат конкретного эфира, доставка в пульт ведущего и модерация |

### Из чего состоит тип

1. **Интерактивная часть.** Движок комнаты, роли и набор действий. Личный звонок может начинаться в P2P-аудио. Групповая встреча использует WebRTC/SFU для микрофонов, камер и экранов.
2. **Компоненты интерфейса.** Панель действий, плитки, демонстрация, чат, вопросы, запись и знакомые состояния загрузки и ошибок. Разработчик переиспользует стандартные компоненты или подписывается на их состояние из своего интерфейса.
3. **Маршруты медиа.** Источник, преобразование и выход определяются независимо. Примеры с одной комнатой: WebRTC между участниками и HLS/CDN для аудитории. Для игрового эфира отдельный вход WHIP, RTP или SRT может идти напрямую на Edge и выходить через WHEP либо HLS.
4. **Возможности ролей.** Для каждого действия определить, кто может его увидеть и выполнить. Например, зритель тренинга смотрит HLS и задаёт вопрос, ведущий отвечает и демонстрирует экран, а модератор управляет очередью. Core проверяет права для каждого действия независимо от UI.

Пример проекта запроса для типа «Тренинг».

```json
{
  "name": "Тренинг",
  "room": { "mode": "group", "transport": "sfu" },
  "components": ["participants", "screenShare", "audienceQuestions"],
  "outputs": [{ "source": "room", "protocol": "hls" }],
  "audience": { "access": "invite", "canAskQuestions": true }
}
```

Core преобразует тип в настройки комнаты и проверяет каждый выход. Выдача доступа к источнику и зрительских ссылок происходит при запуске события. В записи типа хранится ссылка на настройку узла или секрета.

### Этапы реализации

| Этап | Что сделать | Как принять |
| --- | --- | --- |
| 1. Контракт типов | Ввести версионируемый шаблон из `room`, ролей, `components` и ссылок на маршруты. Предусмотреть черновик, предпросмотр итоговой конфигурации и публикацию организацией. | Валидный тип создаёт комнату с указанной версией. Валидация заранее объясняет несовместимость и ошибки прав. Другая организация не может использовать закрытый тип. |
| 2. Первый сквозной тренинг | Групповая SFU-комната. Ведущий включает экран. Egress выдаёт подключаемый HLS-выход. Добавить зрительскую страницу и отдельный допуск в чат с лимитами отправки. | Два ведущих продолжают WebRTC-звонок. Зритель открывает HLS без места в комнате, задаёт вопрос, ведущий отвечает, модератор скрывает сообщение. Проверить срок действия ссылок и ошибку отдельного выхода при работающем звонке. |
| 3. Редактор и SDK | Дать администратору копировать и публиковать типы. Интегратору дать методы получения манифеста и создания комнаты по версии типа. Стандартный SDK рисует компоненты по манифесту, headless SDK позволяет построить свой UI. | На 320 и 1440 px изменения видны в предпросмотре. Новая версия применяется к новым комнатам. Действующая комната сохраняет версию и доступные функции. |
| 4. Внешние источники | Добавить тип игрового эфира. Core назначает Edge, выдаёт доступ издателю и запускает ветви WHEP, HLS и записи по профилю. | Готовый поток RTP или WHIP доходит до назначенного Edge. Второй зрительский узел обслуживает отдельного зрителя. Отказ одной ветви виден в статусе, прочие продолжают работать. |

### Решения перед первым выпуском

| Вопрос | Предлагаемое решение для первого этапа |
| --- | --- |
| Кто составляет и публикует типы? | Администратор организации публикует. Интегратор задаёт конфигурацию через API с правами организации. |
| Что можно менять при создании события? | Название, время, допустимые роли и входы в пределах типа. Обязательные компоненты и права задаёт опубликованная версия. |
| Как изменять уже начавшийся эфир? | Для текущего события меняются управляемые состояния: старт и стоп трансляции, открытие вопросов, модерация. Состав компонентов и маршрутов привязан к версии. |
| Что видят зрители? | В тренинге HLS-плеер и вопросы с возможностью закрытого доступа. Для игровых эфиров можно выбрать WHEP. |
| Что делать при несовместимых кодеках или недоступном узле? | Предпросмотр маршрута показывает необходимое преобразование. Запуск проверяет возможности узла. Ошибка конкретного выхода отражается в его статусе. |
| Что проверять сначала? | Личный P2P-аудиозвонок с согласием на видео, тип «Тренинг» и создание комнаты из SDK. После этого добавлять универсальный редактор маршрутов и внешний игровой вход. |

### Контракт Web SDK для типов комнат

1. **Получение манифеста.** После входа Web SDK получает версию опубликованного типа комнаты, доступные компоненты и разрешённые действия участника. API возвращает только данные его роли. Адреса публикации и ключи остаются в отдельном контуре выдачи доступа.
2. **Одна модель действий.** Стандартный виджет и headless SDK используют одинаковые действия и состояния. Новые компоненты, например «Вопросы зрителей», получают методы и события того же контроллера. Каждый iframe-метод проходит проверку origin и версии возможностей, а Core проверяет права участника.
3. **Отдельный клиент зрителя.** HLS и WHEP открываются в плеере. Клиент зрителя подписывается на состояние выхода и вопросы по отдельному допуску. `join()` остаётся действием для вступления в интерактивную комнату.
4. **Совместимость.** Комнаты без манифеста используют действующие настройки и события. В манифесте отдельно указываются версия формата и версия типа. Клиент может пропустить необязательный компонент, а при отсутствии обязательной возможности показывает понятную ошибку. Проверить стандартный виджет, headless и iframe на одном типе комнаты, включая смену темы, роли и переподключение.
